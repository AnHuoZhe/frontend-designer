# Frontend Designer 架构文档 · 审查报告

> 审查类型：架构审查
> 方案规模：中
> 审查日期：2026-07-17
> 审查者：Hermes（architecture-gap-analysis + product-reviewer 框架）
> 审查项：数据流、失败模式、状态切换、分层检查、运维隐患、上下文工程、记忆系统、工具调用、可靠性

---

## 必须改

### 1. 阶段间数据契约完全缺失——各阶段输入输出格式未定义

文档描述了"加载项目 → 解析后端 → 需求澄清 → 五层设计 → 实现 → 审查 → 合入"的流程，但**没有一个阶段定义了结构化的输入/输出格式**。这会导致每个阶段依赖 LLM 对上一阶段非结构化输出的理解，一致性无法保证。

具体缺口：
- 阶段 A 输出"澄清后的设计需求"——是自然语言段落还是结构化 JSON？包含哪些字段？
- 阶段 B 每层生成"三版选项"——每个选项以什么格式呈现？纯文本描述？mockup JSON？组件草图？
- 阶段 B→C 的交接——五层选定结果以什么格式传给实现阶段？目前只有 .frontend-designer 存了 layer 标签名（如 `"1_priority": "data-first"`），但标签名不包含该层的具体设计决策细节。仅靠标签实现阶段无法知道"data-first 在三选一里到底选了哪种布局"。

**修复方向**：为每个阶段定义明确的输入/输出 JSON Schema。至少需要：
- `feature-extraction-output.json`：功能清单（含端点、参数、响应类型、ui_pattern）
- `design-clarification.json`：用户确认的设计需求（定位、用户画像、风格倾向、参考产品）
- `layer-options-{1..5}.json`：每层三选一的完整描述
- `layer-decisions.json`：用户最终选定的五层决策（不仅是标签，含具体描述）
- `implementation-spec.json`：汇总以上 → 实现阶段的完整输入

### 2. 增量更新的"不改已有部分"假设过于理想化，未处理联动修改

文档 §三 第4步写道："自适应原有设计——新增页面/组件，不改已有部分"。这在实践中几乎不可能：新增一个功能页面通常需要修改导航/侧边栏/路由配置等已有文件。如果后端改了现有 API 的签名，前端对应的 API 调用代码也需要修改，这已经是"已有部分"。

**修复方向**：
- 将策略改为"最小化修改已有部分"，而非"不改已有部分"
- 明确增量更新时的联动范围：路由注册、导航菜单、API client 类型定义
- 增加冲突检测：当 diff 显示已有 API 签名变更时，标记需要同步修改的前端代码位置

### 3. 错误处理和回滚机制完全缺失

整个流程没有一个环节定义了失败后怎么办：

- 后端代码解析失败（不支持的框架、语法错误）→ 整个流程阻塞，无降级方案
- `npm run dev` 验证失败 → 文档只说"验证可运行"，没说失败了是重试生成还是人工介入
- git worktree 创建失败（dirty working tree、磁盘满、路径冲突）→ 无处理
- LLM/Codex API 不可用 → 全管线阻塞，无降级
- 用户在阶段 B 选到一半中断会话 → 无恢复机制

**修复方向**：
- 为每个阶段定义失败模式和回滚策略
- 至少需要有：解析失败时的框架检测提示（"未检测到支持的后端框架，请手动指定"），worktree 创建失败时的环境检查，生成代码编译失败时的重试上限（如最多3次）
- 增加会话中断/恢复机制：将中间状态持久化到 `.frontend-designer/` 目录下的 session-state.json

### 4. 五层设计的锁定传播逻辑过于简单，与实际情况不符

文档称"上层选错推倒下层，下层选错只改当前层。第1层选错全推倒，第5层选错十分钟换掉"。但实际层级间不是严格的单向依赖：

- 第3层（空间分配）的选择可能反向约束第2层（交互流程）的方案——例如选了"无侧边栏顶部导航"后，原来第2层选的"多Tab主从双区"可能需要在顶部导航中重新表达，被迫修改第2层决策
- "下层选错只改当前层"忽略了下层之间也有耦合——改了第4层组件选择，第5层视觉皮肤可能需要微调

**修复方向**：
- 将依赖模型改为有向无环图（DAG），而非严格线性层级，标注可能存在的反向影响
- 每层选中后，给下层生成选项时附加上层入选方案的 context，而不是简单锁死
- 允许"下层修改触达上层建议"——当下层选择确实与上层冲突时，提示用户是否需要回退调整上层

## 建议改

### 5. 后端代码解析器覆盖范围不足

支持的框架只有 FastAPI、Express、Flask、通用扫描。缺少：
- NestJS（TypeScript 后端增长最快的框架之一）
- Go 生态：Gin、Echo、Fiber
- Java 生态：Spring Boot（企业级主流）
- GraphQL、gRPC、WebSocket 端点的识别

**修复建议**：先不扩展框架支持，而是在 SKILL.md 中明确声明"当前支持的框架列表"，并在解析失败时提供"手动描述 API"的降级路径——让用户提供一份简化的 API 清单 JSON。

### 6. 解析输出格式信息密度不足

当前解析输出格式只有 `name, endpoint, user_action, needs_ui, ui_pattern` 五个字段。要实现阶段生成可用的前端代码，远不够用：

- 缺少请求参数（类型、是否必填、默认值）
- 缺少响应类型（数据结构，直接影响表格列定义和表单字段）
- 缺少认证要求（JWT/OAuth/API Key → 影响前端登录流程和请求拦截器）
- 缺少分页信息（前端需要知道用 offset/limit 还是 cursor）

**修复建议**：扩展解析输出 Schema，至少增加 `request_schema`, `response_schema`, `auth_required`, `pagination` 字段。

### 7. frontend-preferences.json 路径硬编码，与"独立项目"定位矛盾

文档 §四 将 `frontend-preferences.json` 路径硬编码为 `E:\work\word\study\product-agent\frontend-preferences.json`。这意味着：
- frontend-designer 作为独立项目，依赖了另一个项目的目录结构
- 在不同机器上这个路径不存在
- 与 forge 的 user-profile.json "同级"的表述暗示了耦合

**修复建议**：偏好文件应由 Codex 的配置机制管理（环境变量或约定的配置目录），而非硬编码绝对路径。或者放在 `~/.codex/frontend-preferences.json` 这样的用户级位置。

### 8. 中期记忆设计缺少设计决策理由的记录

当前记忆体系：
- `.frontend-designer`：记录结果（commit hash、layer 标签名）
- `frontend-preferences.json`：记录偏好历史

两者都记录"选了什么"，但**没有记录"为什么这样选"**。增量更新时，没有决策理由会导致：
- 新功能的设计可能与初始设计隐含的前提冲突
- 无法判断某个偏好是"用户真的喜欢"还是"那次项目特殊"

**修复建议**：在 `.frontend-designer` 中增加 `design_rationale` 字段，为每个 layer 记录一句话理由。在 `frontend-preferences.json` 中为每条历史记录附加项目类型标签（如 "internal-tool", "dashboard"），方便按场景检索而非简单计数。

### 9. 增量更新缺少后端功能删除的检测

文档 §三 只提到"识别后端新增/修改的功能"，没有提到功能删除。后端删了 API，前端对应的页面/组件会成为死代码，积累技术债务。

**修复建议**：增加"检测后端删除的功能 → 标记前端对应页面为待清理 → 在审查报告中列出 → 用户选择保留（降级为静态页面）或删除"。

### 10. 实现阶段缺少 API client 层生成策略

前端需要调用后端 API。谁来生成 `fetch`/`axios` 调用代码？TypeScript 类型定义从哪来？这应该是整个流程中最自动化的部分——既然已经解析了 API 签名，应该直接生成类型安全的 API client，而非让 LLM 在实现阶段根据自然语言描述重新推断 API 调用方式。

**修复建议**：在阶段 C 之前增加一个"API Client 生成"子步骤，从解析输出直接生成 TypeScript 接口定义和 API 调用函数。

### 11. 缺少测试策略

文档完全没有提到测试。生成的代码质量如何验证？只靠 `npm run dev` 确认服务启动远远不够——一个空白页面也能启动。

**修复建议**：在审查阶段增加：
- 基础冒烟测试（每个页面至少能渲染，不报错）
- 与解析出的 API 端点的对照检查（每个需要 UI 的端点都有对应的页面/组件）

### 12. 组件库初始化未覆盖

文档说技术栈默认 shadcn/ui，但 shadcn/ui 不是 npm install 就能用的——需要 `npx shadcn-ui@latest init` 初始化配置，然后逐个 `npx shadcn-ui@latest add` 组件。这个过程需要交互式选择（TypeScript、样式方案、基础颜色等），应该由 frontend-designer 根据第5层的视觉皮肤选择自动完成，而非留给 LLM 在实现阶段摸索。

**修复建议**：在 SKILL.md 中明确 shadcn/ui 的初始化和组件安装流程，根据第5层选择自动映射配置参数。

### 13. frontend-preferences.json 的"连续3次自动默认"机制缺少冷却机制

文档 §四："同类选择连续3次以上 → 自动设为默认选项，设计时直接跳过该层追问"。这意味着用户用同一偏好做3个项目后，第4个项目完全失去了调整该层的机会。用户可能想用同样的布局但不同的配色——此时第5层被跳过是合理的，但第3层也被默认为 sidebar-left 就不一定合理了。

**修复建议**：自动默认应该分维度独立判定，且提供"本次不跳过"的显式选项。或增加冷却期：如果最近一次选择距今超过30天，重新询问。

## 可忽略

- 文档中"组件库可替换"列出了 Ant Design/MUI/Chakra，但没展开说明替换后的影响范围——考虑到这是 1.0 设计阶段，先聚焦 shadcn/ui 是合理的
- 前端代码统一 React + Tailwind + shadcn/ui，未讨论多框架并存方案——1.0 阶段没必要
- 缺少国际化（i18n）和可访问性（a11y）——1.0 阶段可接受，后续版本加
- 审查报告的 docs/frontend-review.md 输出位置在 worktree 内，合入 main 后会跟着进去——从"设计文档跟着代码走"的角度看不算问题
- 五层命名偏抽象（"信息优先级""组件表达"），非技术用户可能看不懂——但目标用户是自己用 Codex 的开发者，抽象层命名可以接受
- 默认技术栈中图标库写了 Lucide React，但未提及如何确保图标一致性——shadcn/ui 默认就是用 Lucide，不额外说明也可以

## 整体判断

架构的核心思路——五层逐层设计 + git worktree 隔离生成 + 增量更新——方向是对的，层级依赖关系的整体方向也合理。但文档目前处于"想法清晰、执行模糊"的状态：定义了做什么，但没有定义怎么做、做错了怎么办。

**三个最核心的结构性问题**：

1. **数据契约真空**——7个阶段没有一个有结构化的 I/O 格式。在一个 LLM Agent 驱动的系统中，没有 Schema 意味着每个阶段都在黑盒传递自然语言，一致性靠运气。这是必须最先解决的问题。

2. **没有失败路径**——整个流程假设一切都成功。后端解析成功、LLM 返回合理结果、代码编译通过、worktree 创建成功。任何一个环节出问题，文档中没有答案。需要为每个阶段设计 fail-fast + 可恢复的机制。

3. **增量更新的"最小修改"假设过于乐观**——实际项目中，新增功能几乎必然会触碰路由、导航、API client 等已有代码。当前设计回避了这个现实，会导致第一次增量更新时就撞墙。

如果这三个问题在进入实现前被解决，剩下的问题可以在迭代中逐步完善。
